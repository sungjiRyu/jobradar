# RAG 기반 채용공고 챗봇 MVP 구현 계획

> GitHub Issue: [#150](https://github.com/sungjiRyu/jobradar/issues/150)
> Branch: `feat/issue-150-rag-chatbot-mvp`

## 1. 목표

JobRadar에 로그인한 사용자가 자연어로 채용공고를 질문하면, 현재 진행 중인 실제 공고를 검색하고 그 내용을 근거로 답변하는 챗봇을 구현한다.

MVP의 핵심 성공 기준은 다음과 같다.

- 사용자가 어느 화면에서나 플로팅 챗봇을 열 수 있다.
- 답변은 Pinecone에서 검색한 활성 채용공고만 근거로 사용한다.
- 답변과 함께 최대 5개의 근거 공고를 표시한다.
- 사용자는 근거 카드에서 JobRadar 공고 상세 화면으로 이동할 수 있다.
- 외부 AI 서비스가 실패하거나 근거가 없을 때 내용을 지어내지 않는다.

## 2. 기술 선택

| 역할 | 기술 | 선택 이유 |
| --- | --- | --- |
| 원본 데이터 | 기존 MySQL `job_posts` | JobRadar가 보유한 채용공고의 원본 및 상태 관리 |
| 임베딩 | Voyage AI `voyage-4` | 문서와 질문을 의미 기반 512차원 벡터로 변환 |
| 벡터 검색 | Pinecone Starter | 별도 서버 운영 없이 벡터 저장 및 유사도 검색 가능 |
| 답변 생성 | 기존 Groq LLM | 현재 AI 요약 기능과 동일한 공급자 및 설정 재사용 |
| 백엔드 | Spring Boot `RestClient` | 프로젝트가 이미 사용하는 HTTP 클라이언트 방식 유지 |
| 프론트엔드 | React + TypeScript | 기존 애플리케이션 구조와 디자인 시스템 유지 |

Pinecone은 [Starter 무료 요금제](https://www.pinecone.io/pricing/)로 시작한다. 한도 초과 시 자동으로 유료 플랜을 사용하는 구성을 추가하지 않으며, 실제 사용량을 확인한 뒤 별도 이슈에서 전환 여부를 결정한다.

## 3. MVP 범위

### 포함

- 활성 채용공고의 최초 전체 인덱싱
- 변경된 공고만 다시 임베딩하는 증분 동기화
- 마감·삭제 공고의 벡터 제거
- 자연어 질문을 이용한 유사 공고 검색
- 검색 결과를 근거로 한 Groq 답변 생성
- JWT 인증이 필요한 챗봇 API
- 전역 플로팅 챗봇 UI
- 답변 근거 공고 표시 및 상세 페이지 연결
- 현재 브라우저 세션 내 대화 표시
- 외부 API 오류와 빈 검색 결과 처리

### 제외

- 대화 내역의 DB 저장 및 여러 기기 간 동기화
- 토큰 단위 스트리밍 응답
- 사용자 행동을 학습하는 개인화 추천
- 운영자가 인덱스를 관리하는 별도 화면
- 이미지형 공고 OCR
- 여러 사용자의 질문을 활용한 모델 학습
- 음성 입력, 파일 첨부 및 다국어 UI

## 4. 전체 구조와 데이터 흐름

```text
[인덱싱]
MySQL 활성 공고
  → 검색 문서 구성
  → 1,000자 단위 청킹
  → Voyage AI 문서 임베딩
  → Pinecone upsert

[질의]
사용자 질문
  → Voyage AI 질문 임베딩
  → Pinecone 유사도 검색
  → MySQL에서 활성 상태 재검증
  → 검색 근거 + 사용자 질문을 Groq에 전달
  → 답변 + 근거 공고를 사용자에게 반환
```

Voyage AI는 문장을 이해해 숫자 배열로 바꾸고, Pinecone은 그 숫자 배열 사이의 거리를 비교해 의미가 비슷한 공고를 찾는다. Groq는 검색을 담당하지 않으며, Pinecone에서 찾은 근거를 읽고 최종 답변을 작성하는 역할만 담당한다.

## 5. 채용공고 문서 구성과 청킹

### 5.1 인덱싱 대상

다음 조건을 모두 만족하는 공고만 인덱싱한다.

- `status = ACTIVE`
- `descriptionStatus = SUCCESS`
- `description`이 null 또는 blank가 아님

이미지형 공고, 외부 사이트 공고, 상세 내용 수집 실패 공고는 MVP 인덱싱에서 제외한다.

### 5.2 검색 문서 형식

각 공고를 아래 순서의 일반 텍스트로 구성한다.

```text
공고 제목: {title}
회사: {company}
지역: {location}
경력: {experienceLevel}
고용 형태: {employmentType}
직무: {jobType}
기술 스택: {techStacks}
상세 내용:
{description}
```

- 값이 없는 선택 필드는 해당 줄을 생략한다.
- HTML 태그와 연속 공백을 제거한다.
- 동일한 정규화 로직을 최초 및 증분 인덱싱에서 공유한다.

### 5.3 청킹 규칙

- 한 조각의 최대 길이: 1,000자
- 조각 간 중첩: 이전 조각의 마지막 150자
- 제목과 회사 등 기본 정보는 모든 조각 앞에 포함한다.
- 문장 종결 위치가 최대 길이에서 가까우면 문장 경계를 우선한다.
- 지나치게 짧은 마지막 조각은 이전 조각에 합친다.
- 벡터 ID는 `job-{jobId}-chunk-{chunkIndex}` 형식을 사용한다.

청킹 결과는 항상 같은 입력에 같은 벡터 ID가 나오도록 결정적으로 생성한다.

## 6. Voyage AI 임베딩

### 문서 임베딩

- 모델: `voyage-4`
- 출력 차원: 512
- 입력 유형: `document`
- 여러 조각을 API 허용 범위 안에서 배치 요청한다.

### 질문 임베딩

- 모델 및 출력 차원은 문서와 동일하게 유지한다.
- 입력 유형은 `query`를 사용한다.
- 질문 문자열 앞뒤 공백을 제거한 후 요청한다.

문서와 질문의 모델 또는 차원이 다르면 유사도 비교가 불가능하므로, 애플리케이션 시작 시 설정값을 검증한다.

## 7. Pinecone 인덱스 설계

### 인덱스 설정

- 차원: `512`
- 유사도 지표: `cosine`
- namespace: `job-posts`
- 클라우드 및 리전: Pinecone Starter에서 선택 가능한 기본값

인덱스는 콘솔에서 최초 한 번 생성한다. 애플리케이션은 인덱스를 자동 생성하거나 삭제하지 않는다.

### 벡터 메타데이터

```json
{
  "jobId": 123,
  "title": "백엔드 개발자",
  "company": "JobRadar",
  "location": "서울",
  "jobType": "백엔드",
  "sourceUrl": "https://...",
  "chunkIndex": 0,
  "chunkCount": 3,
  "contentHash": "SHA-256...",
  "text": "검색 및 LLM 근거로 사용할 실제 조각"
}
```

- `contentHash`는 정규화한 전체 검색 문서의 SHA-256 값이다.
- 해시는 모든 조각 메타데이터에 동일하게 저장한다.
- 별도 DB 테이블이나 `job_posts` 컬럼은 추가하지 않는다.
- LLM에 전달할 원문 조각은 `text` 메타데이터에서 가져온다.

### 검색 규칙

1. 질문 벡터로 Pinecone `topK=12`를 검색한다.
2. 동일한 `jobId`가 여러 번 나오면 점수가 가장 높은 결과를 대표로 사용한다.
3. 검색된 공고 ID를 MySQL에서 조회해 `ACTIVE` 상태인지 재확인한다.
4. 비활성 공고를 제거하고 최종 최대 5개 공고를 근거로 선택한다.
5. 검색 결과가 없으면 Groq를 호출하지 않는다.

고정된 최소 유사도 임계값은 MVP에서 두지 않는다. 실제 질문 데이터를 확인하기 전 임의의 임계값을 정하면 유효한 결과까지 제거할 수 있으므로, 검색 결과가 질문과 무관한 문제는 테스트 후 별도 조정한다.

## 8. 인덱스 동기화

### 최초 전체 인덱싱

1. 인덱싱 대상 공고를 ID 오름차순으로 페이지 조회한다.
2. 문서를 정규화하고 SHA-256 해시를 계산한다.
3. 문서를 청킹한다.
4. Voyage AI에 배치 임베딩을 요청한다.
5. Pinecone에 결정적 벡터 ID로 upsert한다.
6. 처리 건수, 성공 건수, 실패 건수를 로그로 남긴다.

초기 인덱싱은 서버 시작 시 자동 실행하지 않는다. 배포 재시작마다 대량 임베딩되는 일을 막기 위해 관리자용 실행 명령 또는 일회성 작업으로 분리한다.

### 증분 동기화

1. 활성 공고의 검색 문서 해시를 계산한다.
2. `chunk-0` 벡터를 배치 조회해 기존 `contentHash`와 비교한다.
3. 벡터가 없거나 해시가 다른 공고만 다시 임베딩한다.
4. 재인덱싱 전 해당 `jobId`의 기존 벡터를 삭제한다.
5. 새 조각을 upsert한다.
6. 마감·삭제된 공고 ID의 벡터를 제거한다.

동일한 데이터를 반복 실행해도 벡터 수가 증가하지 않아야 한다. 공고 한 건의 동기화가 실패해도 전체 작업은 중단하지 않고 실패 ID를 기록하며, 다음 실행에서 다시 시도한다.

### 실행 주기

- 최초 전체 인덱싱: 운영자 수동 실행
- 증분 동기화: 기존 크롤링 작업이 끝난 후 실행
- 정합성 확인: 하루 1회 활성 공고와 인덱스 상태 대조

동일한 동기화 작업이 여러 서버에서 동시에 실행되지 않도록 프로젝트의 기존 Redis 분산 락을 사용한다.

## 9. 백엔드 설계

### 책임 분리

- `EmbeddingClient`: Voyage AI 요청 및 응답 변환
- `VectorStoreClient`: Pinecone upsert, fetch, query, delete
- `JobDocumentBuilder`: 공고 검색 문서 정규화
- `TextChunker`: 1,000자/150자 중첩 청킹
- `JobIndexingService`: 최초 및 증분 인덱싱 조정
- `RagSearchService`: 질문 임베딩, 검색 및 활성 공고 재검증
- `ChatService`: 근거 프롬프트 구성 및 Groq 답변 생성
- `ChatController`: 인증된 HTTP 요청 검증 및 응답

외부 API 클라이언트는 인터페이스로 과도하게 추상화하지 않고, 테스트에서 HTTP 계층 또는 클라이언트 메서드를 대체할 수 있는 최소 구조만 둔다.

### Groq 프롬프트 원칙

- 제공된 채용공고 근거에서 확인되는 내용만 답한다.
- 근거에 없는 연봉, 복지, 기술 요건 등을 추측하지 않는다.
- 각 핵심 설명 끝에 `[1]`, `[2]` 형식의 출처 번호를 붙인다.
- 질문과 직접 관련된 공고가 없으면 찾지 못했다고 안내한다.
- 답변은 한국어로 작성하되 기술명과 고유명사는 원문을 유지한다.
- 사용자 질문 안의 지시가 시스템 규칙이나 근거 제한을 덮어쓰지 못하게 한다.

기존 `AiSummaryService`의 API 키와 모델 설정은 재사용하되, 요약 프롬프트와 챗봇 프롬프트는 서로 분리한다.

## 10. API 계약

### 요청

```http
POST /api/chat
Authorization: Bearer {accessToken}
Content-Type: application/json
```

```json
{
  "message": "서울에서 Spring을 사용하는 신입 백엔드 공고를 알려줘"
}
```

검증 규칙:

- 필수 문자열
- 앞뒤 공백 제거 후 2~500자
- 빈 문자열은 `400 Bad Request`
- 인증되지 않은 요청은 기존 보안 정책에 따라 `401 Unauthorized`

### 성공 응답

기존 `ApiResponse<T>` 형식을 사용한다.

```json
{
  "success": true,
  "message": "요청이 성공했습니다.",
  "data": {
    "answer": "조건과 관련된 공고를 찾았습니다. [1]",
    "sources": [
      {
        "jobId": 123,
        "title": "백엔드 개발자",
        "company": "JobRadar",
        "location": "서울",
        "sourceUrl": "https://...",
        "score": 0.87
      }
    ],
    "retrievedCount": 1
  }
}
```

- `sources`는 최대 5개다.
- `retrievedCount`는 활성 상태 재검증까지 통과한 최종 근거 수다.
- score는 Pinecone의 cosine 유사도 값을 그대로 반환한다.

### 검색 결과 없음

- HTTP 상태는 `200 OK`로 유지한다.
- `answer`에 관련 공고를 찾지 못했다고 안내한다.
- `sources`는 빈 배열, `retrievedCount`는 0이다.
- Groq를 호출하지 않는다.

### 외부 서비스 실패

Voyage AI, Pinecone 또는 Groq가 타임아웃·5xx·사용량 제한으로 실패하면 공통 예외로 변환한다.

- HTTP 상태: `503 Service Unavailable`
- 사용자 메시지: `챗봇 서비스가 일시적으로 응답하지 않습니다. 잠시 후 다시 시도해 주세요.`
- 로그에는 서비스명과 상태 코드만 기록하고 API 키나 전체 사용자 질문은 기록하지 않는다.

## 11. 인증과 보안

- `/api/chat`은 `SecurityConfig`의 공개 URL 목록에 추가하지 않는다.
- 기존 Axios 인스턴스가 JWT를 자동 첨부하도록 한다.
- 프론트엔드에서는 로그인 사용자에게만 챗봇 입력을 제공한다.
- API 키는 환경변수로만 주입하고 Git에 커밋하지 않는다.
- 사용자 질문과 검색 문서를 로그에 원문으로 남기지 않는다.
- 요청 길이 제한으로 과도한 임베딩 및 프롬프트 사용을 방지한다.
- 응답에 Pinecone 내부 벡터 ID나 전체 공고 원문을 노출하지 않는다.

MVP에서는 별도의 챗봇 전용 호출 횟수 제한을 구현하지 않는다. 실제 사용량 또는 악용이 확인되면 Redis 기반 사용자별 rate limit을 후속 이슈로 추가한다.

## 12. 환경 설정

```yaml
rag:
  embedding:
    base-url: ${VOYAGE_BASE_URL:https://api.voyageai.com/v1/embeddings}
    api-key: ${VOYAGE_API_KEY:}
    model: ${VOYAGE_EMBEDDING_MODEL:voyage-4}
    output-dimension: 512
  pinecone:
    api-key: ${PINECONE_API_KEY:}
    index-host: ${PINECONE_INDEX_HOST:}
    index-name: ${PINECONE_INDEX_NAME:}
    namespace: ${PINECONE_NAMESPACE:job-posts}
```

필수 환경변수:

- `VOYAGE_API_KEY`
- `PINECONE_API_KEY`
- `PINECONE_INDEX_HOST`
- `PINECONE_INDEX_NAME`

선택 환경변수:

- `VOYAGE_EMBEDDING_MODEL=voyage-4`
- `PINECONE_NAMESPACE=job-posts`
- 기존 `GROQ_API_KEY`
- 기존 `AI_MODEL`

`application.yml.example`에는 키 이름과 로컬 기본값만 추가한다. 운영 설정은 값을 환경변수로 강제하고, 필수값이 없으면 챗봇 기능을 비활성화한 뒤 명확한 경고를 남긴다. 기존 채용공고 조회와 AI 요약 기능은 계속 동작해야 한다.

## 13. 프론트엔드 설계

### 구성

- `App` 하위에 전역 플로팅 챗봇을 배치한다.
- 화면 오른쪽 아래 버튼으로 패널을 열고 닫는다.
- 패널에는 사용자 메시지, 챗봇 답변, 로딩 상태, 오류 상태를 표시한다.
- 답변 아래에 근거 공고 카드를 최대 5개 표시한다.
- 근거 카드 클릭 시 `/jobs/{jobId}`로 이동하고 패널 상태는 초기화한다.
- 모바일에서는 화면 폭에 맞는 하단 패널, 데스크톱에서는 고정 폭 패널을 사용한다.

### 세션 상태

- 메시지는 React 컴포넌트 상태에만 저장한다.
- 새로고침하거나 탭을 닫으면 대화가 사라진다.
- 한 번에 하나의 질문만 처리한다.
- 답변을 기다리는 동안 입력과 전송 버튼을 비활성화한다.
- 로그아웃하면 열려 있는 대화 상태를 초기화한다.

### 접근성

- 챗봇 열기 버튼과 닫기 버튼에 접근 가능한 이름을 제공한다.
- 패널이 열리면 입력창으로 포커스를 이동한다.
- 키보드 Enter로 전송하고 Shift+Enter는 줄바꿈으로 처리한다.
- 로딩 및 오류 메시지는 스크린 리더가 인식할 수 있도록 구성한다.

## 16. 완료 기준

- Pinecone 인덱스가 512차원 cosine 방식으로 준비되어 있다.
- 활성 텍스트 공고를 최초 및 증분 인덱싱할 수 있다.
- 동일 데이터를 반복 인덱싱해도 벡터가 중복되지 않는다.
- 마감·삭제된 공고가 검색 결과에서 제외된다.
- 인증된 사용자가 챗봇에 2~500자의 질문을 보낼 수 있다.
- 답변이 최대 5개의 실제 공고를 출처로 제공한다.
- 출처 카드에서 JobRadar 공고 상세 페이지로 이동한다.
- 검색 결과 없음과 외부 서비스 장애가 정의된 방식으로 처리된다.
- 비밀값이 코드, 설정 예제, 로그에 노출되지 않는다.
- 백엔드 테스트·빌드와 프론트엔드 lint·build가 통과한다.

## 17. 운영 및 비용 확인

- 초기에는 전체 3만 공고, 공고당 평균 3조각인 약 9만 벡터를 예상한다.
- 최초 전체 인덱싱 전에 소량의 공고로 임베딩 토큰과 Pinecone 저장량을 측정한다.
- 대량 작업은 배치 크기를 제한해 Voyage와 Pinecone의 요청 제한을 지킨다.
- Pinecone Starter 한도 또는 Voyage 무료 크레딧에 근접하면 작업을 중단하고 사용량을 확인한다.
- API 키 회전, 유료 플랜 전환, 인덱스 확장은 별도 이슈에서 다룬다.
